# json-repair

Read JSON that is not quite JSON.

A Rust port of the Python package [`json-repair`](https://pypi.org/project/json-repair/), pinned to
**0.61.7** and held to its answers byte for byte. Give it a trailing comma, a missing brace, a bare
key, single quotes, smart quotes, a code fence, or prose wrapped around the whole thing, and it
returns the value the text was reaching for.

```rust
use json_repair::{Value, loads};

let value = loads(r#"{answer: "Paris", "why": 'the capital',}"#)?;
assert_eq!(value.get("answer"), Some(&Value::Str("Paris".into())));
# Ok::<(), json_repair::Error>(())
```

Language models are the usual source of such text, but nothing here knows that: the input is a
string and the output is a value.

## Why a port rather than another repairing parser

Several Rust crates repair malformed JSON, and each repairs it its own way. This one is not a new
set of heuristics — it is *these* heuristics, so a program moving from Python gets the same answers
for the same input, including the strange ones.

Which means the tests cannot be a reading of the original. They are generated by **running** it:

- every case recorded as the bytes `json.dumps` writes, so `7` stays apart from `7.0`, a key keeps
  the position it was first assigned, and an integer wider than a machine word stays exact;
- the **repair log** recorded alongside each value, because a value says where a parse arrived and
  the log says which branch took it there;
- the upstream project's own test suite, replayed;
- and a differential fuzzer over a grammar of malformed JSON, both sides compared.

## Getting a value out

`loads` returns a `Value`, the Rust spelling of what Python's `json` module produces.
`repair_json` returns the text `json.dumps` would write for it instead:

```rust
assert_eq!(json_repair::repair_json("{a: 1,}")?, r#"{"a": 1}"#);
# Ok::<(), json_repair::Error>(())
```

`Repair` carries the options — strict mode, streaming, a JSON Schema to repair against.

## The `serde` feature

Off by default. With it on, `Value` implements `Serialize` and `Deserialize`, converts to and from
`serde_json::Value`, and `loads_as` deserializes straight into your own type:

```rust,ignore
#[derive(serde::Deserialize)]
struct Answer { answer: String, score: i32 }

let parsed: Answer = json_repair::loads_as("{answer: 'Paris', score: 7,}")?;
```

It does not replace `repair_json`. `serde_json` writes JSON its own way; Python's `json.dumps` puts
a space after every comma and colon, escapes everything outside `\x20`-`\x7e`, and renders a float
with `float.__repr__` — `1e+16`, not `10000000000000000`. Reproducing those bytes is the point.

## What is not reproduced

JSON Schema **validation**. The Python package delegates that to `jsonschema`, a separate library,
and raises when it is not installed. Reimplementing a validator here would be a different project,
so it is a `SchemaValidator` you plug in — and with none plugged in this answers exactly as a Python
environment without `jsonschema` does.

## Two places Rust cannot follow Python

- **A lone surrogate.** `"\ud800"` is a valid Python `str` and not a valid Rust `String`, so an
  escape naming one yields `LONE_SURROGATE` where Python keeps the surrogate.
- **Recursion depth.** Python answers deep nesting with `RecursionError` at a depth belonging to the
  *caller's* stack rather than to the library — measured at 330 nested arrays from a top-level call,
  247 nested objects, and 317 arrays from forty frames deeper. There is no single number to match,
  so the limit here is a fixed `MAX_DEPTH`.
